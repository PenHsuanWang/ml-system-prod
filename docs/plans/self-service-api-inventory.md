## Error contracts and operation gaps

| Domain | Observed error definitions / transport |
| --- | --- |
| Identity | HTTP detail for AuthenticationFailed 401, AuthorizationDenied 403, UserNotFound 404, UserAlreadyExists 409, IdentityUnavailable 503 and InvalidIdentityInput 400; DTO validation 422. |
| Catalog | ML domain envelope; Forbidden 403, SchemaMismatch 422, CapacityExceeded 429, DiscoveryFailed 503, DiscoveryTimeout 504; outer authentication may use HTTP detail 401. |
| Sources and ingestion | ML envelope including INGESTION_INVALID and SOURCE_REJECTED 400, tenant/resource NOT_FOUND 404, immutable/conflicting state 409; auth 401/403. Adapter execution failures become job error_code and state rather than a synchronous acquisition HTTP timeout. |
| Training | ML envelope including invalid intent/key 400, invisible job 404, idempotency/state conflict 409, pending capacity 429; auth 401/403. Async training results appear through job/model resources. |
| Registry and deployment | ML envelope including unknown resource 404, approval/evidence/route conflicts 409, deployment capacity 429, permission denial 403. |
| Dataset metadata | Permission denial 403, missing/invisible dataset 404; raw data access is not provided by this metadata route. |
| Prediction | Explicit per-status response schemas and verified runtime behavior are recorded in the standard and WP1 report, including 413 and correlation exceptions. |

Framework 422 handling is registered by the runtime factory. Unexpected database/SDK exceptions
must not be assumed to use a declared domain error envelope.
The evaluation HTTP API reads persisted evaluation evidence; evaluation execution is performed
by TrainingSupervisor. Feature engineering is implemented by EBMDatasetPreparationService and
the operator builder, with no feature-engineering HTTP route.

## Gateway, Serving, flags and profiles

Gateway GET / redirects to /docs. GET /docs, /redoc and /openapi.json are framework documentation
routes, public, and DOCUMENTATION_ONLY. Public GET /health/live reports liveness;
GET /health/ready checks SQL and Identity, returning 200 or 503.
POST /api/v1/prediction/predict is IMPLEMENTED, requires current session/ml:predict and tenant route,
and now documents request, success/error schemas and synthetic examples in English.
Tests/ml/test_prediction_gateway_docs.py validates HTTP success, auth, tenant, payload/validation,
bounded capacity/deadline, upstream failure and proxy behavior.
Internal fixed Serving also has GET /health/live, GET /health/ready and POST
/api/v1/prediction/predict. Serving's health is an internal identity check and its prediction
service enforces tenant/endpoint and ml:predict. Its raw readiness fields are not a public model
catalog. test_pytorch_e2e.py and ebm/test_prediction_boundary.py exercise those boundaries.

Default ML Management modules are identity, training, registry, deployment and datasets.
Ingestion is registered only with its configuration enabled; source-management routes follow it.
Catalog is opt-in through ML_CATALOG_ENABLED plus approved connection/policy files.
The test injection factory mounts only supplied optional services.
Generic substrate kernels/jobs/exports can be enabled through template settings; they do not
provide ML DatasetBuilder, approved training recipe or active prediction endpoint discovery.
Compose publishes Gateway on 8001 and Management on 8000. Reverse proxies may supply a root_path.
Kubernetes changes runtime endpoint resolution but retains the same logical HTTP contracts.

## WP3 implementation delta — 2026-11-27

The Phase 0 route inventory above remains a historical baseline. WP3 adds Management-only
GET ingestion jobs/snapshots, dataset families/versions/version detail/lineage. Existing source
browsing and exact dataset-version lookup remain available. SQL performs tenant/owner scope,
filters, ordering and bounds. New EBM builds atomically bind verified receipt evidence in the
existing SQL catalog; old missing evidence stays incomplete. Full receipts additionally require
input visibility, otherwise restricted status withholds source identities. See the
[API workflow](../ml-runbook.md#dataset-discovery-and-lineage-wp3),
[plan](dataset-discovery-lineage.md) and [evidence report](../reviews/wp3-dataset-discovery-report.md).
Later work packages build on this baseline. The table above records the current trajectory
for training, governance, and explicit dataset build orchestration. Target-environment
production qualification remains separate.
